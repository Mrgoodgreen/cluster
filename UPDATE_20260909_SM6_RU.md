## Что применяется после обновления

- Новая модель: `pipeline/models/etalon_rf_scene_20260909.pkl`, SHA-256 `bf4dbc1eeae99f9708292837d4cc921226a62ebf4adbd36f8b303fbde15ee6a5`. Это те же байты модели, что использовались в просмотренном полном прогоне.
- RF использует общий контекст сцены, а предсказание выполняется порциями. При нехватке памяти уменьшается порция, без пересчёта контекста. Геометрия остаётся с динамическими внешними тайлами и GPU-окнами HDBSCAN.
- Все исходные классы сбрасываются в Default 1 перед геометрической классификацией.
- Ground 2, vegetation 3/4/5, Building 6, Noise 7, Vehicle 91. Автомобили и шум разделены, как в эталонах и проверочном запуске.
- Бюджет памяти учитывает RAM и ограничения cgroup контейнера. Если сам LAS/общий контекст не помещаются, выдаётся явная ошибка; скрытого перехода к другим RF-признакам нет. Это не полностью потоковая обработка произвольно большого файла на любой RAM.
- Воркер проверяет готовые LAS по числу и координатам точек, создаёт `.tls-complete.json`. Ошибки чтения/записи проверки повторяются штатным механизмом. Менеджер не выдаёт одновременно два файла с одинаковым выходным путём.
- Принятый дизайн перенесён в рабочий React-интерфейс менеджера: боковое меню, сводка задач, таблица с поиском и фильтрами, создание задачи, выбор/создание папок, автоматический выходной путь, карточка задачи и журнал. Отмена и повторный запуск работают через API; повторный запуск создаёт новую задачу. Время отображается по Москве. Поиск и фильтры работают по всей базе, а не только по открытой странице; сводка показывает все задачи. Пример `preview/tls-cluster-preview.html` сохранён, но Docker собирает именно рабочий React-интерфейс.
- Версии основных вычислительных библиотек закреплены в `pipeline/GPU_0_0_1/constraints-tested.txt` и применяются при сборке воркера, включая scikit-learn 1.7.2, использованный для сохранённой модели.

Размер геометрических тайлов по-прежнему зависит от доступной RAM. На другом лимите памяти могут измениться геометрические границы и часть классов; общий RF-контекст устраняет только зависимость RF от его порций. Побитное совпадение полного результата на разном оборудовании этим выпуском не гарантируется.

## Нужно ли менять переменные

**Для безопасного обновления недостаточно только собрать образ: проверьте существующее окружение каждого worker stack.** Новые значения по умолчанию уже включены в Dockerfile/compose, однако старые значения из `.env` или Portainer имеют приоритет.

В том месте, где у вас настроены переменные воркера, выставьте:

```dotenv
RF_REFINER=/opt/tls/pipeline/models/etalon_rf_scene_20260909.pkl
RF_CONTEXT_MODE=scene
CARS_TO=91
NOISE_TO=7
TILE_WORKERS=1
RF_MAX_TILE_POINTS=0
```

Назначение:

- `RF_REFINER` — путь к одобренной модели **внутри контейнера**. Старый путь `.../etalon_rf_refiner.pkl` продолжит выбирать старую модель, поэтому его нужно заменить, если он уже задан.
- `RF_CONTEXT_MODE=scene` — новая настройка общего контекста всего облака. `windows` оставлен для явного возврата к прежнему оконному RF, результат которого может отличаться.
- `CARS_TO=91` — в серверном снимке было значение 7. Для нового RF обязательно 91. Если оставить 7, новая обёртка остановится с подсказкой до начала классификации.
- `NOISE_TO=7` — класс шума. Задаётся отдельно от машин; для режима scene требуется 7.
- `TILE_WORKERS=1` — один внешний геометрический участок за раз. Не увеличивайте для воспроизведения проверенного режима на одном GPU.
- `RF_MAX_TILE_POINTS=0` — автоматический бюджет. В `scene` положительное значение ограничивает порцию предсказания (не более 1 млн), а не размер общего контекста. В `windows` это предел RF-окна. Старое значение 5 млн не требуется.

Другие низкоуровневые переключатели (`MAX_POINTS_MONO`, `MAX_TILE_POINTS`, `TILE_M`, `TILE_OVERLAP_M`, `RF_TILE_M`, `RF_OVERLAP_M`, `FORCE_TILE`, `HDBSCAN_BACKEND`) вручную добавлять не нужно. Если ранее задавали их для экспериментов, проверьте: они могут переопределить штатную автоматическую настройку. `RF_TILE_M` и `RF_OVERLAP_M` в режиме scene не используются. Менеджеру новые обязательные переменные не нужны. Порты и SMB-подключения остаются прежними.

Не заменяйте рабочий `.env` целиком файлом `.env.example`: в примере демонстрационные значения адресов и SMB-доступа. При работе через Portainer сохраните используемый способ передачи `.env`/переменных stack и измените только перечисленные значения.

## Обновление через Git и Portainer

Используйте новый архив `cluster_update_20260909_sm6_ui.zip` вместо предыдущего `cluster_update_20260909_sm6_approved.zip`. Он содержит полную разницу с исходным снимком `cluster_deployed`, включая одобренную модель и новый интерфейс.

**Если предыдущий пакет sm6 уже установлен и шесть переменных воркеров настроены**, для этого обновления достаточно пересобрать и пересоздать только менеджер с новым тегом `sm6-ui-20260909`. Воркеры и модель относительно предыдущего пакета не изменены. Выполните шаги 1–3, затем только действия для менеджера в шагах 5–7; проверьте новый интерфейс, открытие задач и выбор папок. Новых переменных для интерфейса и миграции базы нет.

**Если обновляетесь с исходной серверной версии**, выполните все шаги ниже, включая оба образа и настройки воркеров.

1. Дождитесь окончания текущих заданий, временно не ставьте новые. Сохраните текущие теги образов и рабочие `.env` для отката.
2. Распакуйте архив в корень репозитория cluster. Проверьте `git status` и список в манифесте. Существующие данные и `.env` заменяться не должны.
3. Закоммитьте перечисленные файлы. Если в репозитории нет других незавершённых изменений, можно выполнить из его корня:

   ```bash
   git add -A
   git diff --cached --stat
   git commit -m "Integrate the new cluster dashboard and release the approved SM6 GPU classification pipeline"
   git push
   ```

   Если другие изменения есть, добавляйте только пути из манифеста. В архиве есть модели размером примерно 204 МБ каждая: убедитесь, что ваш Git-сервер принимает такие файлы. Если в репозитории принят Git LFS для моделей, используйте его существующие правила; при сборке должны быть скачаны реальные PKL, не текстовые LFS-указатели.

4. Обновите рабочие переменные всех воркеров шестью значениями выше. Если stack использует собственную копию compose в редакторе Portainer, перенесите туда новые строки окружения и теги образов из `deploy/*/docker-compose.yml`.
5. Пересоберите **менеджер и все воркеры** из новой Git-ревизии. Если сборку выполняете вручную, на соответствующем Linux-сервере из корня обновлённого репозитория:

   ```bash
   docker build -f manager/Dockerfile -t tls-classify-manager:sm6-ui-20260909 .
   docker build -f worker/Dockerfile -t tls-classify-worker:sm6-20260909 .
   ```

   Менеджер собирайте на его сервере. Воркера соберите на каждом worker-сервере либо распространите собранный образ через используемый registry и укажите его имя в stack. Команды не требуют переустановки NVIDIA Toolkit, драйвера или настройки SMB. Обычный build с кэшем допустим: изменённые файлы/ограничения зависимостей инвалидируют соответствующие слои.
6. В Portainer откройте manager stack, обновите Git-ревизию и примените compose с образом `tls-classify-manager:sm6-ui-20260909`; выполните Update/пересоздание сервиса. Затем аналогично обновите worker stacks с `tls-classify-worker:sm6-20260909` и новыми переменными. Если образы собирались только локально, используйте их на нужном Docker-хосте, не пытайтесь скачать эти локальные теги из публичного registry. При работе через свой registry используйте его адрес и распространённые туда теги.
7. **Простого Restart недостаточно.** Нужны новый образ, обновлённые настройки и пересоздание контейнера. Само получение Git-кода Portainer не доказывает, что образ пересобран; проверьте выбранный тег и фактическое окружение. Не запускайте отдельный дублирующий compose stack поверх уже управляемого Portainer сервиса.
8. На worker-сервере проверьте только нужные переменные, не выводя SMB-пароли:

   ```bash
   docker exec tls-classify-worker python3 -c 'import os; print({k:os.getenv(k) for k in ("RF_REFINER","RF_CONTEXT_MODE","CARS_TO","NOISE_TO","TILE_WORKERS","RF_MAX_TILE_POINTS")})'
   docker exec tls-classify-worker sha256sum /opt/tls/pipeline/models/etalon_rf_scene_20260909.pkl
   ```

   Контрольная сумма должна совпадать с указанной выше. Если контейнер назван иначе, используйте его имя.
9. Создайте тестовую задачу на небольшой LAS в **новую выходную папку**. В журнале должны быть `MANDATORY RESET`, сведения о GPU, путь к новой модели, затем строки `[RF-SCENE]`. После успешного завершения рядом с LAS появляется `.tls-complete.json`.
10. Старые корректные результаты по тем же путям будут проверены и пропущены, а не переклассифицированы новой моделью. Для нового результата используйте новую выходную директорию. Некорректный существующий LAS даёт `OUTPUT_INVALID` и сохраняется для разбора; он не перезаписывается автоматически.

Миграция базы и удаление Docker volumes не требуются. Не удаляйте manager_data или SMB-тома. Для отката верните прежние теги образов и прежние переменные в Portainer, затем пересоздайте контейнеры; исходные данные и база сохраняются.

Сам алгоритм после этого прогона не изменён: упаковка включает ту же модель и те же RF-признаки; изменены значения по умолчанию и добавлена ранняя проверка настроек.

Пройдены 35 регрессионных тестов Python, включая поиск, фильтры и пагинацию API, и production-сборка нового фронтенда. Собранный интерфейс проверен в headless Edge с изолированным тестовым API: создание задачи и папок, выбор путей, автоматический выходной путь, поиск и страницы, отмена, повторный запуск, обновление журналов, ошибки API и мобильный экран. Проверка не запускала веб-сервер и не отправляла задания вашим воркерам. Архив проверяется распаковкой поверх серверного снимка и сравнением хешей исходников и модели. Реальная Docker-сборка и работа с вашим SMB/Portainer здесь не запускались; выполните контрольную задачу после обновления.
